## Decisions

### `Field` takes one `onCommit`, not an `onChange`/`onSubmit` pair

- **Choice:** a single callback that carries the value with the commit.
- **Why:** the first version had both, and a choice button called them in the same tick. The
  parent read its `draft` state before React had applied it, so **every multiple-choice answer
  would have committed `undefined`** — the purpose question, income type, city tier, all of
  them. Passing the value through with the commit removes the window rather than papering over
  it with a `useEffect`.
- **Rejected:** keeping the pair and reading the value from an effect or a ref. Both work and
  both leave a trap for the next person.
- Caught by reasoning about the code, not by a test — there is no DOM test setup here.

### Every question's field is keyed by question id

- **Choice:** `<Field key={question.id} …>`.
- **Why:** without it, two money questions in a row reuse the same component instance and the
  second arrives pre-filled with the first one's text. React reuses by position and type, and
  both questions render the same type at the same position.
- **Would be wrong if:** we ever want a field to deliberately carry over — no case for it here.

### The must set is asked in order; everything after it is ranked live

- **Choice:** `Flow` asks the first unanswered, applicable must question; once those are done it
  asks `nextQuestions(answers, 10)` for the top-ranked unskipped one, re-ranked after every
  answer.
- **Why:** without the must set the engine invents rather than estimates, so those are not
  negotiable. After that, what is worth asking depends entirely on what has been said — a
  borrower who owns nothing should never be asked what it is worth.
- **Skipped questions are never re-offered.** Someone who declined once should not have to
  decline repeatedly.
- **Assumes:** the ranking is stable enough not to thrash. `tests/flow.test.ts` pins that no
  question is ever asked twice.

### An explicit exit after the essentials

- **Choice:** once the must set is done, an "I have answered enough — show me the answer" button
  appears above the fold of the remaining questions.
- **Why:** answering everything is **20–21 screens** for these three borrowers (10 essential,
  the rest optional). That is a lot, and a flow with no visible end is one people abandon. The
  optional tail is genuinely useful — every question in it still moves a number, or the engine
  would have dropped it — so the answer is an exit, not a shorter list.
- **Rejected:** hard-capping the optional questions at five. That would silently deny a borrower
  who wants a tighter answer the means to get one, and the cap would be arbitrary.
- **Would be wrong if:** the tail feels long enough in practice that people quit rather than
  press the exit. Flagged to the user to judge from the actual walk, since that is a question
  about the experience, not the arithmetic.

### Confidence copy says what confidence is not

- **Choice:** three states from the engine's own `confidence.thresholds`, with copy that states
  outright that answering questions which change nothing does not make the answer more certain.
- **Why:** every form a borrower has filled in has trained them to read a progress bar as a
  reward. This meter measures the width of the answer, and "low" on a genuinely wide answer is
  correct rather than a failure — Ravi is the live example.
- The component only draws; the thresholds stay in the rule tables.

### A missing answer and a real zero are not the same statement

Found by the user reading the screen, on the first questions of the flow. Fixed in `a9e18e0`,
committed separately so it reads on its own in the history.

- **What was wrong:** before an income is given the engine returns `need-more-info` and a safe
  amount of zero, and the meter printed it as a figure — **"Right now: safe to carry
  nothing."** — under each of the first four questions. It also labelled the answer "Wide" and
  explained that its top and bottom were different situations, when there was no answer yet to
  be wide.
- **Why it matters more than it looks:** zero is the correct value for "we have not been told
  an income". It is not the correct *sentence*. One reading means "we do not know yet", the
  other means "you cannot borrow anything" — and a borrower told the second on question one
  would be right to close the page. This is the same failure the project already names: an
  answer that is obviously wrong costs more than one that is quietly wrong.
- **Choice:** while the verdict is `need-more-info`, the meter says "Nothing to narrow yet",
  shows an empty grey bar, and prints `verdict.why` and `verdict.nextStep` — the engine's own
  sentences — instead of any figure.
- **Rejected:** hiding the meter entirely until an income arrives, which loses the explanation
  of what is missing and why; and special-casing the copy inside the component, which would let
  the screen and the engine drift apart on what "not enough yet" means.
- **Assumes:** `need-more-info` is the only verdict that means "no answer yet". It is — every
  other branch has an income behind it.
- **Would be wrong if:** a future rule returns a genuine, meaningful safe amount of zero while
  the verdict is `need-more-info`. Nothing does today.
- **Guarded by** two tests in `tests/flow.test.ts`: nothing numeric is reported across the four
  partial answer states, and a figure *does* appear as soon as an income exists — so it cannot
  regress in either direction.

### A blank upper bound on a range means "the same"

- **Choice:** in the money-range field, leaving the "good month" box empty sets `hi = lo`.
- **Why:** a salaried borrower earns the same every month and should not have to type it twice.
- **Assumes:** nobody means "unbounded" by leaving it blank, which would be an odd reading for
  an income question.

### The lakh echo under money fields

- **Choice:** `800000` echoes as "₹8 lakh" beneath the input; thousands below that.
- **Why:** the engine works in rupees and Indians think in lakh, and that gap is where a zero
  goes missing. Typing ₹80,000 when ₹8,00,000 was meant is the most likely input error in this
  whole app, and it would be invisible afterwards — every downstream number would simply be
  wrong by 10x and internally consistent.

### The personas stay reachable, relabelled

- **Choice:** the start screen offers Start, and underneath, the three borrowers "to see a
  finished answer without answering anything".
- **Why:** they are how the personas get checked and how a reader reaches a finished answer in
  one click. Calling them a reviewer's door rather than presenting them as the product is the
  honest framing.

## Verification

- `npx tsc --noEmit` clean, `npm run build` succeeds, **262 tests passing**.
- `tests/flow.test.ts` replicates the flow's selection logic and pins, for all three borrowers:
  - walking the questions reaches **the same verdict** as handing the engine every answer at
    once, and **the same product**. If those diverged the flow would not be collecting answers,
    it would be changing them;
  - the flow terminates and never repeats a question;
  - the must set is asked before anything optional;
  - a borrower who skips **every** question still gets `need-more-info` with a next step, rather
    than a crash or a silent zero.
- Flow lengths measured: Priya 20 questions of 28 (6 skipped), Ravi 21 (4), Anita 19 (4).

### Not verified

- **The browser walk at 375px** — phase 5's exit condition. The layout is built mobile-first
  and the money fields carry `inputMode="numeric"`, but no horizontal-scroll check has been
  run. Handed to the user.
- Nothing in `ui/` has a DOM test. The two React bugs here were caught by reading the code, and
  the confidence-meter defect above was caught by the user reading the screen. That is now
  three defects in this phase and the last two of phase 4, all of the same kind: the engine's
  numbers were right and the screen said something false about them. A jsdom setup is the
  obvious next investment if this continues past the take-home — but it is worth noting that
  none of the five would have been caught by testing the engine harder.
